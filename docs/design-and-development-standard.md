# 经管实证研究助手：设计与制作标准

- 版本：1.2
- 日期：2026-09-15
- 状态：沿已确认的 v1.1 原则及用户授权实施的入口设计更新
- 适用范围：本项目后续产品设计、Skill 编写、代码实现、结果解释和验收。
- 来源：用户提供的初始设计及本轮设计评审。本文将评审结论转化为执行标准；文中功能均为要求，不表示已经实现。

## 1. 项目定位与成功目标

帮助经管实证新手，把研究问题转化为有依据的分析方案，完成可复现执行，并理解结果能够支持什么结论。

首要用户是已有表格数据、会少量分析操作，但尚不能独立组织完整实证流程的经管学生。

同时覆盖只有大概研究方向、尚未确定具体问题和变量组合的用户：帮助其盘点现有数据，形成有依据的候选研究方案，并判断实际结果对各项研究判断的支持程度。

核心价值：

1. 自动执行可明确规定的操作。
2. 用实际计算和证据检查数据、模型执行及推断条件。
3. 解释当前问题、决策依据和下一步。
4. 保留方案、执行、结果和解释之间的追溯关系。

不得把回归数量、显著结果数量、检验完成比例或论文生成速度作为主要成功标准。

## 2. 首版范围

以宿主 Agent 的自然语言对话为主入口，一个 research 入口与 design/evidence/analysis/interpret 四个专项 Skills 共用状态和材料。软件维护请求按开发任务处理，实际研究才生成个人目录。

阶段 A 交付研究准备：材料阅读与方案比较的方法、CSV 结构检查、科研记录、任务、实际文件版本、检查点和本地接续。阶段 B 沿同一项目补齐正式描述统计、默认 Python、可选 Stata 的线性固定效应执行、运行包和独立数值核对；阶段 A 不等于统计闭环完成。

每项研究用 literature/data/research 管理文件，保存讨论、可见来源、更正和下一步。无数据概念草案不能获得正式执行确认；恢复方案形成新版本并重新确认，恢复旧结果仍待数值核验。外部结果也保留结果暴露记录。实际宿主兼容和至少三名初学者试用另行验收，未验证不得宣称通过。

V0.1 从已有表格数据开始，支持企业年度面板上的描述统计和线性固定效应关联分析。首版仅选择一个估计执行后端；具体后端在实现方案中依据可用环境确定并记录。

首版必须交付：

| 产物 | 必须包含的内容 |
| --- | --- |
| 研究设计卡 | 研究问题、分析目标、研究对象、时间范围、变量角色、结论边界 |
| 候选方案比较表 | 方向与可用字段的对应关系、候选问题、方案差异、可行性、数据缺口、优先级及理由 |
| 变量与样本说明 | 概念、定义、单位、时间口径、来源、缺失含义、样本规则、版本 |
| 数据审计报告 | 唯一键、合并关系、时间覆盖、分布、缺失、样本变化、可用变化 |
| 分析方案 | 模型、控制变量、固定效应、标准误、样本及各项选择理由 |
| 可复现运行包 | 代码、输入版本、环境信息、参数、结构化结果、日志 |
| 结果解释与下一步 | 效应量、不确定性、适用范围、待解决问题及优先行动 |

以下不纳入首版自动执行范围：全面文献检索与全文抽取、DID、IV、PSM、因果机制识别、自动异质性搜索、整篇论文生成、多估计后端和自主多代理协作。

涉及首版不支持的方法时，系统应说明支持边界并保留研究需求，不得降格为普通固定效应回归后仍作原定因果解释。

## 3. 架构与模块职责

采用一个协调器、若干职责明确的 Skills 和可验证的程序工具。模块不必一一对应独立代理。

| 层次 | 职责 | 主要产物 |
| --- | --- | --- |
| 研究设计 | 问题、概念、测量、对象及识别假设 | 设计卡、变量字典 |
| 分析执行 | 合并、变量构造、样本构建、估计 | 代码、分析样本、结构化结果 |
| 质量检查 | 数据、执行、推断条件与解释边界检查 | 审计记录、待解决问题 |
| 工作流管理 | 状态、版本、依赖、决策与下一步 | 状态记录、决策记录、证据链接 |

证据追溯、方法检查和状态管理必须贯穿流程。文献模块为设计提供证据，写作模块只消费经过检查且未过期的结果。

每个模块在实现前必须明确：输入、输出、前置条件、失败状态、依赖和验收方式。

## 4. 标准工作流

项目接入与方向澄清 → 数据盘点与测量检查 → 候选研究方案比较 → 研究设计卡与分析方案确认 → 执行 → 审计 → 结论支持程度评估 → 针对剩余问题继续分析。

允许返回上游修改，但必须保存修改原因并更新下游状态。

### 4.1 先明确分析目标

模型推荐之前，必须区分描述、关联、因果和预测。不得仅凭企业年度面板结构默认因果解释。

因果问题还需明确研究对象、比较状态、观察时期及目标效应。预测任务需要单独的验证设计，不直接套用关联分析流程。

### 4.2 用研究威胁组织后续分析

后续分析应由具体问题触发，例如反向因果、测量误差、样本选择、共同冲击或机制解释不足。

每项建议必须说明：针对什么问题、需要什么条件、提供什么证据、不能解决什么问题。

不得把滞后解释变量、IV、PSM、DID 列为统一的“内生性检验套餐”。不得默认每项研究都需要机制、异质性或相同数量的稳健性检验。

### 4.3 从研究方向与现有数据生成候选方案

这是首版核心入口。用户不必预先提供完整假设、X/Y 或模型，系统应先做以下工作：

1. 澄清方向中最关心的经济现象和可能的解释，保留相互竞争的解释，不预设必须成立的结论。
2. 读取现有数据及说明，盘点可用字段、经济含义、观测单位、时间覆盖、可匹配标识、缺失状态和变化来源；字段名称不足以确认含义时标记待核实。
3. 将经济概念映射到实际可构造的指标，说明代理指标与概念之间的距离，不因字段可用就认为它能有效测量目标概念。
4. 默认提出少量有实质区别的候选方案，通常为 2—3 套；若数据只支持一套或暂不支持任何方案，应如实说明，不凑数。
5. 按问题价值、测量质量、数据覆盖、可用变化、识别条件及工作量比较，在查看目标回归结果前给出优先级理由。

每套候选方案必须包含：

| 项目 | 内容要求 |
| --- | --- |
| 研究问题与目标 | 具体研究什么，属于描述、关联、因果还是预测 |
| 可检验判断 | 预期关系、理由、竞争解释；缺乏方向依据时允许非定向探索 |
| 数据映射 | X/Y 对应的实际字段、构造规则、单位、时间和来源 |
| 样本与比较 | 哪些主体、哪些时期、利用何种差异进行比较 |
| 模型与条件 | 候选模型、控制变量角色、固定效应、推断方式及必要条件 |
| 可行性与缺口 | 现有数据可做、需补数据、或当前无法判断，以及具体原因 |
| 结果解释边界 | 哪些结果与判断一致，哪些构成反证，哪些仍无法区分解释 |
| 方案关系 | 不同研究问题，还是同一问题下的替代测量、敏感性分析或探索性分支 |

不得通过任意排列全部变量、自动逐步筛选控制变量、遍历样本切分来生成研究方案。不同结果变量或代理指标可能对应不同问题，不能一律称作稳健性检验。

超出首版执行能力的设计可作为候选建议保留，但应明确需要的数据、方法支持和进一步论证，不自动执行。

### 4.4 用结果评估结论支持程度

运行前保存候选判断、主要分析和比较目的；运行后生成“判断—证据”对照表。每条判断绑定方案、运行、系数或图表、效应量、区间、样本及主要限制。

分别解释：

- 方向与幅度：估计方向是否与判断一致，幅度是否有实质意义。
- 精度：区间是否足以区分有意义的正向、负向或接近零的效果；精度不足时说明无法判断，不把不显著等同于没有关系。
- 敏感性：合理方案之间的差异来自测量、样本、控制条件还是其他变化；不得仅按显著与否投票。
- 解释层级：证据支持描述、条件关联还是具备额外识别依据的因果判断。

可以使用“与判断一致”“出现相反证据”“证据不足以区分”“对合理设定敏感”等文字概括，但必须附具体依据，不能仅按 p 值自动赋类。

允许根据结果修订研究理解或提出新问题；必须标记为结果之后的探索，保留原方案和全部运行。多项检验的数量、选择过程及适用的多重检验处理或后续独立验证需求须说明，不能把探索性发现直接包装成预先提出且得到确认的结论。

系统应能建议继续验证、补充数据、缩小结论或暂停某条路线，不得把获得显著结果作为探索停止条件。

## 5. 方法与审计标准

程序负责计算和验证，语言模型负责解释、组织证据和提出建议。不得将模型口头判断包装成已执行的统计检查。

### 5.1 数据和测量

- 合并前核对键及预期关系，合并后检查丢失与意外扩行；不得静默去重。
- 记录每一步观测数、主体数及适用时的处理组变化，并说明顺序和原因。
- 区分明确为零、未披露、不适用、匹配失败等原始状态；不得未经规则确认统一填零。
- 区分经济发生时间、会计期间和信息可获得时间，检查时间错配与未来信息误用。
- 极值处理、样本剔除、频率转换和变量变换必须绑定已记录的规则。
- 原始数据保留不变；处理产物可以追溯到输入版本和构造步骤。

### 5.2 模型与推断

- “使用了固定效应或聚类标准误”只说明设置存在，不等于设置合理。
- 检查在实际固定效应和控制变量条件下，解释变量是否仍有可用于估计的变化。
- 聚类选择应结合研究设计、误差相关结构和簇的信息量；不得机械默认企业聚类。
- 运行成功、推断适当、识别可信是不同维度，必须分别表达。
- 不得以非显著预趋势证明平行趋势成立，不得以滞后解释变量普遍宣称解决内生性。
- 机制一致性证据与因果机制证据必须区分。

### 5.3 审计问题分类

| 类别 | 示例 | 必须采取的行为 |
| --- | --- | --- |
| 执行错误 | 意外多对多扩行、估计失败、非有限数值、输出解析失败 | 停止依赖该结果的后续步骤，保留错误证据 |
| 需要解释的诊断 | 大量样本流失、处理簇少、剩余变化有限 | 展示证据、影响及处理选项，不机械宣告模型无效 |
| 需要论证的假设 | 平行趋势、排除限制、无遗漏混杂 | 记录假设、论据、可能违反情形和未解决问题，不自动认证 |

不得以单一红绿灯或总分替代具体审计证据。

### 5.4 文献和结果解释

- 文献提取应绑定原文位置；缺少全文或定位依据时，明确证据不足。
- 未检索到某个 X→Y 关系只能形成候选问题，不能自动证明研究贡献或文献空白。
- 结果文字必须绑定实际运行与具体结果字段，不从聊天记忆补写系数。
- 效应解释必须匹配单位、变量变换、交互项和模型形式。
- 不将“系数乘以 X 的标准差”当作全部模型通用的经济意义公式。
- 报告效应量及不确定性；不显著结果不得触发自动寻找显著设定。
- 关联结果不得改写为已识别的因果效应。

## 6. 方案、运行与探索记录

### 6.1 分析方案

至少记录：方案标识与版本、研究目标、样本规则、变量版本、缺失处理、模型、固定效应、标准误、分析目的、确认状态和选择理由。

### 6.2 运行记录

至少记录：运行标识、方案版本、输入数据版本或校验值、代码版本、执行环境、参数、适用时的随机种子、实际样本、实际估计选项、警告、输出位置和执行状态。

系统必须比较实际运行与分析方案；存在偏离时，应明确标记并处理后再生成正式解释。

### 6.3 探索记录

保存所有实际执行的设定及其修改原因，区分事先计划和看到结果后的新增分析。不得静默丢弃不显著或不符合预期的运行。

语法、路径等技术修复可在既定方案内自动完成；改变样本、变量定义或估计方法属于研究决策，必须记录并按确认规则处理。

## 7. 状态、依赖与证据追溯

状态至少包括：待做、运行中、完成、失败、需要决策、已过期、不适用。执行状态与检查状态分别保存。

“完成”仅表示对应执行或产物完成，不代表因果假设获得证明。

必须维护依赖关系。例如修改 X 定义后，受影响的变量数据、回归、表格与文字都应标记过期，完成必要重跑和检查后才能恢复使用。

结果应能追溯为：解释或表格 → 结构化估计结果 → 运行记录 → 分析方案与代码 → 输入数据。

规范目录不能单独构成可复现性证明。可复现性必须通过实际重跑验证。

## 8. 新手交互与决策边界

每个重要决策提供：推荐做法、依据、影响和剩余不确定性。优先询问用户了解的制度事实和数据事实，再解释对应方法选择。

默认输出三层信息：

1. 当前结论与最值得先处理的问题。
2. 结合当前数据的原因解释。
3. 可展开的数字、代码、文献和日志证据。

已确认方案内的处理、重跑和导表可以自动完成，不重复请求确认。改变研究对象、测量口径、样本规则或识别策略等实质事项时，应形成明确决策并取得必要确认。

不得要求新手仅通过点击“批准”承担无法理解的方法判断。

不使用“总体研究完成 63%”等指标暗示研究可信度。展示产物状态、关键阻塞、证据与下一步理由。

## 9. 实现与扩展规则

- 第一条原型链必须覆盖：给出大概方向 → 盘点现有数据 → 比较可行方案 → 明确规则 → 执行分析 → 评估结论支持程度并追溯表格 → 修改口径后正确重跑。
- 先完成上述闭环，再扩大功能范围。
- 每增加一种估计方法，必须同步增加适用条件、检查规则、解释边界与验证案例。
- 方法限制应由规则和程序检查落实，不能仅写在提示词中。
- GitHub 项目只有经过具体仓库、版本、许可证和能力核查后，才能作为实现依赖；未经核查的介绍只作灵感。
- 不以“首次工程化经管实证”或“市场没有同类产品”作为未经验证的产品事实。

## 10. 首版验收标准

| 验证案例 | 必须观察到的行为 |
| --- | --- |
| 合并意外形成多对多关系 | 检出扩行并定位来源，不静默去重 |
| X 被所选固定效应完全吸收 | 说明该系数无法估计，不编造结果解释 |
| 加入控制变量后样本下降 | 按缺失原因说明变化，提供共同样本比较选项 |
| 回归出现数值错误 | 异常输出不进入正式表格与结果文字 |
| 修改变量定义 | 受影响的结果与文字被标记过期 |
| 获得不显著结果 | 解释区间与精度，不自动搜索显著设定 |
| 文献没有可定位依据 | 标记证据不足，不补造页码或结论 |
| 相同数据与环境重跑 | 在事先明确的数值容差内复现结果 |
| 实际执行偏离方案 | 检出并展示差异，不默认为方案已正确落实 |
| 中断后继续工作 | 从有效状态恢复，不误用失败或过期产物 |
| 只有大概方向与字段说明 | 生成与实际数据对应的候选方案，明确待核实项，不编造字段或识别条件 |
| 数据只支持一套或不支持任何方案 | 如实说明限制和最小补充需求，不强行生成多个方案 |
| 多套方案结果不同 | 按问题、测量、样本与设定解释差异，保留全部结果，不按最小 p 值选择结论 |
| 结果精度不足或方向相反 | 区分证据不足与相反证据，允许缩小结论或暂停路线 |
| 查看结果后新增假设 | 记录提出时间及原因，标记探索性，保留原有分析 |

验收使用预先定义的测试数据、故意注入的错误和独立核对的参考结果；每项记录输入、预期、实际结果与证据。不得用“代码运行无报错”替代全部验收。

用户验证还须检查：新手是否理解样本变化、是否能说明模型在比较什么、是否能复现输出。速度是辅助指标。

## 11. 标准维护
