## 审阅摘要

**交付形式：用户 clone 仓库，在 Codex 或 Claude Code 中打开仓库根目录，发送研究请求，即可由智能体带着开始研究。**

**核心价值：兼具研究助手的执行能力和指导老师的解释能力，帮助初学者逐渐理解并组织研究。**

**当前工作目录的用途：维护和发布 GitHub 工具仓库。** 本稿描述的个人研究目录与科研记忆由最终用户在自己的使用副本中生成；本维护目录仅承载产品源码、入口、Skills、模板、文档、测试和教学示例。

建议采用以下设计：

1. **一个统一入口，四个专项 Skills。** 同一个宿主智能体根据用户要求、当前进度和材料自动选择相应指导，不要求学生选择模块。
2. **Agent 负责研究推理，程序负责实际计算和记录。** LLM 根据研究问题、文献和数据形成方案；复用固定检查工具，并按已确认方案生成项目脚本，经实际运行与核验后交付。
3. **同一份研究规范，两套宿主适配。** 首版支持 Codex 与 Claude Code，保留扩展其他 Agent 的接口。
4. **研究进展保存在项目文件中。** 自动保存重要对话信息、研究决定、实际产物与下一步，支持跨会话及宿主顺序接续；每项研究用 `literature / data / research` 管理文献、数据和分析过程，并保留相互关联的版本。
5. **第一版不开发自己的 CLI/Web 产品入口，不在仓库中接入模型 API。** 现有命令和脚本可作为 Agent 内部工具，用户使用自然语言。

审阅时优先看第 1—5 节的使用体验与职责，第 6—10 节说明可落地性，第 11 节列出建议确认的设计选择。v0.3 的重点是第 4.7 节自动选 Skill、第 6.1—6.3 节目录与科研记忆、第 6.6—6.7 节版本和项目管理；相应验收见第 10.5 节。

## 1. 产品目标与第一版边界

### 1.1 面向什么用户

经管科研初学者，可以只有一个研究兴趣，也可以已有数据、论文、分析结果或老师意见。系统应识别其当前起点，协助推进，不要求先具备完整假设、变量组合或计量方案。

指导应贯穿实做：读论文时说明证据如何支持研究问题；合并数据时解释样本变化；选模型时说明比较对象；读结果时解释效应量、精度和结论边界。根据用户的提问调整讲解深度，已经理解或确认的内容不重复讲授。

### 1.2 第一版如何划定范围

| 能力 | 第一版设计范围 |
| --- | --- |
| 对话与研究设计 | 接受模糊方向，帮助识别问题、概念、数据需求和可行方案；研究讨论可覆盖超出当前计算能力的方法 |
| 文献证据 | 阅读用户提供的资料；宿主具备检索能力时做针对性查证，记录来源和定位；不承诺完整系统综述 |
| 正式分析执行 | 延续现有标准：企业年度面板、描述统计和 Python 线性固定效应关联分析，采用一条经验证的统计执行路线；固定工具与 Agent 生成的项目脚本共享同一方案、运行和核验规则 |
| 已有结果讨论 | 可以协助阅读用户提供的表格与代码；明确哪些结果只是外部提供、哪些已核对或复现 |
| 报告交付 | 对话解释与可读 Markdown 材料为基础；Word、Excel 等在宿主相关工具可用时按需交付 |
| 暂不纳入 | 自建用户界面、仓库直连 LLM API、自主多智能体协作、DID/IV/PSM 等方法的正式执行后端、整篇论文自动生成 |

**“能开始研究”与“已经完成分析”分别验收。** 入口和 Skills 完成后可以先试用研究准备；正式宣称第一版研究闭环可用，还须通过分析、结果核对和修改后重跑的验收。无需把每项科研操作预先封装成通用软件模块，但生成了脚本或得到成功退出码，也不等于结果已经核对。

### 1.3 环境前提

用户已安装并能正常使用目标 Agent，在该 Agent 中以仓库根目录作为工作项目，并允许它读取相关材料。打开文件夹本身不会启动后台研究，需要用户发送首条请求。

研究讨论不以统计环境、付费数据库或外部连接器齐备为前提。需要计算或检索时再检查相应能力；缺少工具应保留已能完成的工作，并说明最小补充条件。所有模型调用由宿主 Agent 提供。

结构化建项和恢复仍需能运行本地状态工具。若尚不能运行，允许先讨论，并在有文件写入能力时暂存明确标注的讨论稿；同时说明结构化保存尚未完成，环境就绪后核实并登记。不能在这种情况下声称已获得完整跨会话恢复能力。

### 1.4 维护仓库与用户使用副本

当前维护者已明确：本工作目录用于开发、审阅、测试和维护 GitHub 仓库。这里讨论研究功能，是在设计产品；提到文献、数据、结果或记忆，不据此启动一项实际研究。开发测试需要的模拟研究项目使用临时目录，固定教学样例可以保留在 `examples/`。

发布内容包括可复用的入口、Skills 及配套资源、程序、空白模板、说明、测试和教学示例。用户 clone 后获得这些文件；只有用户在自己的副本中真正开始研究，才生成 `research-projects/` 下的文献、数据、分析产物和进度记录。

因此，维护仓库的 Git 版本记录跟踪产品开发，用户项目的本地版本记录跟踪具体科研工作。科研材料的排除规则随工具一并发布，供用户使用；它不表示维护者需要在当前文件夹里开展研究。开发计划、设计审阅稿和产品验证记录属于维护内容，可以随仓库提交。

## 2. 用户入口：第一次和下一次

### 2.1 首次使用

入口读取现有研究项目清单及用户指定的材料，按情况进入：

| 用户起点 | 入口行为 | 当轮应给出的实际帮助 |
| --- | --- | --- |
| 只有兴趣 | 先讨论关心的现象和背景，每轮优先解决一个关键疑问 | 更具体的问题表达、需要了解的数据或事实 |
| 已有数据 | 查看字段、样本单位、覆盖和说明，核实关键测量 | 数据盘点、可研究的问题与主要缺口 |
| 已有论文 | 阅读与当前问题有关的章节并定位证据 | 论文问题、设计、发现及与用户研究的关系 |
| 已有回归结果 | 查看表格、变量口径、代码和样本信息 | 哪些可以解释、哪些需要补充或复核 |
| 老师给了反馈 | 对照反馈与当前材料，识别实质要求 | 有依据的修改顺序，并执行已明确授权的工作 |

若材料已包含答案，先读材料，减少提问。不让学生填写完整“建项问卷”，也不要求先选好 X/Y。程序标识、参数和状态字段由 Agent 整理。

新研究目录仅在用户确实要开始一项研究时建立。普通概念咨询不自动建项。用户只说“开始研究”且方向未定时，可以先交流，明确初步方向后建项。

### 2.2 示例：只有一个方向

用户：想研究企业数字化与风险，但是不知道怎么开始。

助手示意回应：

> 可以先从你关心的现象入手。你是注意到数字化可能让企业经营更稳定，还是可能让企业承担更多风险？如果有课程案例、老师建议或参考论文，也可以从那里开始。

获得背景后，结合已有材料讨论风险的具体含义、候选测量和竞争解释。提出候选问题时，区分文献支持、数据事实和仍待查证的推测；不在第一轮直接把数字化指数和某个风险指标填进回归模板。

### 2.3 示例：已有材料

用户：数据和两篇参考论文在这个文件夹，帮我看看能做什么。

助手应先读取相关文件，再给具体反馈，例如说明论文中的概念能否对应到数据列、年份是否匹配、哪些关键定义仍不明。存在说明缺口时问有针对性的问题；文件夹里的教学样例不得当作用户真实数据。

### 2.4 继续研究

用户说“继续上次研究”时：

1. 若指定了项目，打开该项目；若只有一个项目，核实状态后继续；若存在多个且意图不明，先让用户选择，避免混用。已有项目状态损坏时先检查和恢复，不将它视为不存在而另建同名项目。
2. 读取研究状态、最新有效材料、未解决问题和上次下一步，检查文件及版本是否仍匹配。
3. 用几句话说明上次做到哪里、当前最需要处理什么，并推进此前已授权的下一步。
4. 发现中断、文件变化或旧结论过期时，处理受影响的环节；保留能够继续使用的材料。

每个实质工作单元结束时保存进展，不依赖用户最后说“保存”或“结束”。恢复能力来自项目记录，不依赖某个宿主的聊天记忆。

## 3. 项目入口设计

### 3.1 两个入口文件

| 文件 | 职责 |
| --- | --- |
| 根目录 `AGENTS.md` | 共用入口：判断用户在做研究还是开发仓库，定位研究项目，加载统一研究 Skill，规定共享文件与续接规则 |
| 根目录 `CLAUDE.md` | 通过 `@AGENTS.md` 复用入口，补充 Claude Code 的项目 Skill 路径及必要的宿主差异 |

入口不装入全部研究手册。研究请求进入统一 Skill；软件开发、测试、仓库解释等请求按用户实际任务处理，不把开发者强行带进研究问答。

**拟定的共用入口内容要点（供审阅，不是已生效指令）：**

> 本项目帮助经管初学者开展研究。用户提出研究需求时，以研究助手和指导者的方式服务：结合材料推进工作，解释关键选择的理由和证据。
>
> 先识别这是新研究、已有研究的继续，还是对某份材料的专项讨论。研究任务读取 `econbiz-research`；根据当前问题读取相应专项 Skill。用户无需知道这些内部名称。
>
> 原始材料、当前方案与结果均从项目文件核实。记录实质进展、研究决定和下一步；使用经过校验的工具保存状态。数据变化后核查受影响的结果。
>
> 每项研究使用已登记的文献、数据和研究工作目录。保存本轮重要对话信息与实际产物，维护版本及引用关系；用户下次要求继续时，读取保存记录并核实当前有效性。
>
> 根据当前需要解决的问题选择 Skill。需要综合材料、形成新方案或执行分析时，先明确本轮输入、输出及检查方法；普通概念解释沿当前对话处理，不强制建立整套任务文件。
>
> 已确认方案内的操作继续完成。实质研究选择先解释推荐、影响和不确定性，再记录用户决定。尊重用户已经给出的授权和约束。
>
> 用户要求开发或维护本仓库时，处理开发任务；不自动创建研究项目或启动研究流程。

### 3.2 兼容与默认加载

Codex 的项目 Skills 放在 `.agents/skills/`，Claude Code 的放在 `.claude/skills/`。以 `.agents/skills/` 为维护源，发布前由维护工具生成并提交 `.claude/skills/` 中的对应副本，检查正文和配套资源一致。

生成在维护者侧完成，用户 clone 后无需生成、复制或全局安装。首版使用普通文件，避免把跨平台体验建立在符号链接权限上。共享规范保存在仓库内，平台副本按仓库根目录定位；禁止写入开发者电脑的绝对路径。

自然语言是主入口。研究请求由项目指令要求加载统一 Skill，减少只依赖名称匹配的不确定性。若宿主没有自动发现 Skill，可在同一项目中按入口读取相应 `SKILL.md`；README 提供一句兜底提示：“请按本项目 AGENTS.md 和研究入口 Skill 开始。”

首版兼容承诺以真实宿主测试为准，记录版本、系统和能力。普通 Claude 网页对话、其他 Agent、所有操作系统均不自动继承“已验证兼容”的结论。

## 4. Skills 分工

### 4.1 选择：一个统一入口 + 四个专项 Skills

| Skill | 何时使用 | 负责什么 | 主要交付 |
| --- | --- | --- | --- |
| `econbiz-research` | 开始、继续、组织一项研究；跨阶段反馈和项目管理 | 理解用户起点、定位项目、自动选择 Skills、安排下一步、保持指导风格、保存记忆、协调文件和版本管理 | 当前问题、已知与未知、行动安排、进展记录和版本对照 |
| `econbiz-design` | 明确研究问题、测量、候选设计，或讨论修改设计 | 将经济现象、理论解释、文献和数据条件组织成有实质差别的方案；解释选择理由 | 问题说明、候选方案比较、变量定义、可执行方案草稿 |
| `econbiz-evidence` | 阅读论文、核查方法或事实、判断证据支持程度 | 使用用户材料及可用检索工具；区分作者主张、实际发现和本项目推论，保存来源定位 | 文献卡、判断与来源的对应关系、待查证事项 |
| `econbiz-analysis` | 盘点数据、构造变量和样本、执行确认的分析、复现结果 | 复用检查工具、生成并运行项目脚本，检查键、缺失、合并、样本、估计与实际执行参数；解释操作的研究影响 | 数据/样本说明、审计、运行记录、结构化结果 |
| `econbiz-interpret` | 解释结果、比较方案、回应反馈、修改结果文字 | 把实际结果与事前判断对照，解释效应量、精度、敏感性与结论边界 | 结果解释、判断—证据表、下一步建议 |

这些 Skills 是同一个 Agent 按需读取的工作方法，不分别启动五个智能体。学生可以直接问专项问题；统一入口只补充必要上下文，不把每次提问都重新送回第一阶段。

### 4.2 各 Skill 的输入与完成条件

| Skill | 最小输入与前提 | 完成条件 | 信息或工具不足时 |
| --- | --- | --- | --- |
| research | 用户请求；已有项目则附当前状态 | 当轮请求得到处理，重要信息与下一步可接续 | 项目不明则定位；未明确研究则先讨论 |
| design | 初步兴趣即可开始；正式分析方案另需真实字段与样本依据 | 方案说明问题、理由、测量、比较、条件、缺口和边界；可执行状态与研究讨论状态分开 | 保留待验证的概念草案，列最小补充需求 |
| evidence | 需要核查的判断或指定资料 | 结论绑定实际读到的来源位置，阅读范围明确 | 无全文则限定于已读材料；不能把检索摘要当作完整验证 |
| analysis | 盘点需可读数据；执行需已确认的具体方案及可用后端 | 产物与输入/方案版本相符，执行和检查结果分别记录 | 保留错误和已有成果；不补造计算结果 |
| interpret | 用户指定结果；正式解释需有效结果及口径 | 每个数值可追溯，解释匹配单位与模型，说明结果支持到什么程度 | 外部结果可作条件性讨论；缺少依据的数值解释列为待核查 |

### 4.3 研究推理与程序检查如何合作

LLM 形成候选问题及设计论证；文献 Skill 核实依据；分析工具提供实际字段、覆盖、缺失及可用变化。设计 Skill 综合这些材料提出少量有实质差异的方案，通常 2—3 套，信息不足时可以少于两套。

概念草案可以包含尚无字段或当前无法执行的方法，但必须标明缺口。只有完成真实数据绑定和可执行条件检查后，才能转成正式分析方案。结构校验通过仅证明格式和所检查条件符合要求，不认证理论贡献、测量有效性或因果识别。

现有按规则产生描述/关联路线的功能保留为教学样例或辅助参照。它不决定 Agent 可以想到哪些问题，也不作为研究方向入口的必经步骤。

### 4.4 比较过的组织方式

| 组织方式 | 判断 |
| --- | --- |
| 所有内容写进一个大 Skill | 起步简单，但长期容易一次加载过多内容、方法与维护边界模糊 |
| **统一入口 + 四个专项 Skills** | **推荐。** 连贯指导与按需加载兼顾，便于分别检验设计、证据、计算和解释 |
| 每个研究步骤都做成独立 Skill/独立 Agent | 首版协调成本高，容易让学生面对碎片化流程；当前无此必要 |

每个 `SKILL.md` 只保留能力说明、关键判断依据、输入输出和必要的工具/资料指引。长方法说明、样例和格式放在按需读取的资源中，避免把问答顺序写死。

### 4.5 五个 Skills 的操作规程

以下规定的是要完成的研究工作，允许根据材料在步骤之间往返。已经有有效产物时直接复用，不能为了走一遍流程而重复提问、计算或建表。

#### 4.5.1 `econbiz-research`：识别任务并保持连续指导

1. **先读什么：** 用户请求、当前研究进展及其对应状态；与本轮有关的文件、老师意见或未解决事项。检查是否为开发仓库任务。
2. **怎样判断：** 找出当前真正需要解决的问题，例如研究对象不清、测量依据不足、数据异常或结果难以解释。按第 4.6—4.7 节选择所需 Skill，不把全部 Skills 每轮都加载一遍。
3. **怎样推进：** 对综合材料、新方案、分析执行等任务建立简短任务卡，明确输入版本、目标、输出及检查；已确定的范围自动完成，只向用户询问影响研究选择的缺失信息。
4. **交付什么：** 对本轮问题的回答、对应材料和最值得做的下一步；重要进展进入项目记录。
5. **怎样检查：** 回看实际使用的材料、产生的文件、检查结果和未解决事项。记录“需要但尚未读到的资料”及其影响；技能数量和文件数量不作为完成指标。

#### 4.5.2 `econbiz-design`：从兴趣形成有依据的方案

1. **先读什么：** 用户关心的现象、相关文献证据卡、数据说明、盘点事实及已有研究决定。没有材料时可以从概念讨论开始。
2. **怎样判断：** 区分研究目标，提出可能的解释和竞争解释；说明概念对应哪些指标、代理测量会遗漏什么、利用什么比较回答问题。
3. **怎样推进：** 需要文献依据时调用 evidence，需要核实覆盖或变化时调用 analysis。根据实际条件形成少量候选方案，比较问题价值、测量质量、可执行性和工作量，不按潜在显著性排序。
4. **交付什么：** 候选方案比较表及推荐理由。信息齐备的方案登记为可审阅的分析计划；未绑定数据或当前不支持执行的设计仍作为讨论草案保存。
5. **怎样检查：** 每项关键判断注明来自文献、数据、用户说明或待验证推测；检查字段存在、时间口径和比较条件。不能从“没找到同类论文”直接推断研究创新。

#### 4.5.3 `econbiz-evidence`：把文献连接到具体研究判断

1. **先读什么：** 本轮要核实的判断与用户提供的材料，优先定位相关摘要、定义、方法和结果，不机械逐篇全文摘要。
2. **怎样判断：** 分清理论解释、测量依据、经验发现和方法条件。记录读到的范围、原文位置、研究样本及支持的具体判断；只有题名或元数据时不能提取研究发现。
3. **怎样推进：** 使用已授权且可用的检索/阅读工具补证据；对冲突结果比较定义、样本和识别条件。摘要、用户笔记和全文证据分别标识，不补造引用或定位。
4. **交付什么：** 可复用的文献证据卡和“判断—来源”对应表。每条证据说明它如何改变本项目的设计选择，以及哪些问题仍未解决。
5. **怎样检查：** 核对来源身份、实际内容与主张是否匹配，保留间接或相反证据。交接给 design 或 interpret 时一并提供适用边界。

#### 4.5.4 `econbiz-analysis`：让计划成为可核对的实际分析

1. **先读什么：** 当前方案及确认范围、字段和样本定义、输入校验值、可用环境；盘点本身不要求已有回归方案。
2. **怎样判断：** 区分可复用的固定检查与需要生成的项目代码。对原始数据、转换、合并、样本构造和估计分别明确输入输出；正式估计先通过方案与方法支持检查。
3. **怎样推进：** 按第 7.4 节生成、保存并执行脚本。解释和处理数据问题；结果数值、样本数、选项和警告从实际运行读取，发现异常保留日志并处理。
4. **交付什么：** 运行包、样本变化说明、结构化结果和核对记录。输出与方案版本、代码版本、数据和环境建立联系。
5. **怎样检查：** 对照计划与实际执行；核对样本、系数、标准误、区间和表图来源。第一次采用新的实现路径时，以独立参考核对并重跑；不以同一函数重复调用代替独立核验。

#### 4.5.5 `econbiz-interpret`：解释结果并形成研究表达

1. **先读什么：** 事前研究判断、有效方案、实际结果、单位和变量变换、样本与诊断；外部表格先注明尚未复现。
2. **怎样判断：** 分别评估方向与幅度、估计精度、合理设定间的差异和解释层级。精度不足、相反证据和结论敏感分别讨论。
3. **怎样推进：** 先写判断—证据对照，再形成清楚的文字。需要补充文献或计算时回到对应 Skill；看到结果后新增的问题登记为探索。
4. **交付什么：** 面向学生的解释、可按需使用的结果段落、图表说明和下一步。每项建议说明针对什么问题，以及需要哪些条件。
5. **怎样检查：** 数值、方向、单位和样本均可追溯；文字不超出证据。工作记录与正式段落分开，待办事项、操作说明、占位内容不混入成稿；不自动扩展成整篇论文。

### 4.6 按当前问题组织任务

| 当前问题 | 优先读取 | 达到什么条件后继续 |
| --- | --- | --- |
| 研究现象、对象或目标不清 | design | 能表达当前要回答的问题，未知项已明确 |
| 某个理论、指标或事实缺乏依据 | evidence | 有可定位依据，或明确证据不足及其影响 |
| 数据覆盖、缺失、测量构造不明 | analysis，必要时返回 design | 获得实际数据事实，形成可审阅的处理选择 |
| 已确认方案待执行 | analysis | 实际运行并核对，产物状态与结果相符 |
| 结果的含义或不同方案差异不明 | interpret，按需补充 evidence/analysis | 能说明证据支持到哪里及下一步 |
| 修改指标、样本或研究问题 | design + analysis | 保存修订理由，检查旧结果有效性，完成必要重跑 |

任务卡仅用于需要持续记录的工作：综合多份材料、形成或修改研究方案、运行分析、交付带证据的结果说明。普通概念解释或明确的小修改不强制建卡；若会改变已有研究材料，则在既有记录中更新即可。任务检查由当前 Agent 完成，首版不因任务变大而自动要求多代理。

### 4.7 根据用户要求自动选择 Skill

**默认自动选择，保留用户显式指定。** 研究入口根据用户想完成的事情、已有项目状态、实际材料和前置条件选择所需 Skills。宿主可按 Skill 描述发现相关能力；项目入口再负责明确路由，减少仅靠关键词匹配造成的遗漏。此为预期行为，不能承诺模型在所有请求上零误判。

| 用户可以直接说 | 内部处理示例 |
| --- | --- |
| “这几篇论文有什么共同点，能用来设计我的研究吗？” | evidence 整理证据，design 结合现有数据讨论研究选择 |
| “数据有没有问题？合并以后为什么变多了？” | analysis 读取数据与处理记录，实际检查键和合并关系 |
| “这个回归怎么解释？” | interpret 核对结果口径；缺少必要信息时调用 analysis 补查 |
| “老师建议换个指标，帮我比较一下。” | design 检查概念和测量；analysis 核实可构造性及影响，再讨论修订 |
| “继续上次的项目。” | research 读取科研记忆和当前状态，再选择所需专项能力 |
| “把文献整理好，保留这次方案，和上一版比较。” | research 管理目录与版本，按材料内容调用 evidence/design |

不要求用户确认内部 Skill 选择。只有研究对象、任务范围或关键含义不明确时才澄清；加载多个 Skills 也不代表同时启动多个代理。某个 Skill 或其所需工具不可用时如实说明，完成独立可做的部分，不假装已调用。

自然语言开始、显式点名和跨阶段切换均应测试。用户指令优先于默认路由，已明确的研究需求不能因关键词命中而被改写；自动选 Skill 不等于自动批准新的研究方案。

## 5. 如何像指导老师一样交流

### 5.1 每次帮助的基本形态

优先提供“目前可以怎么判断 → 结合材料解释为什么 → 最值得做的下一步”。根据任务决定是否附表、数字、代码或文献定位，不强制每次回答使用固定标题。

- 先了解学生知道的事实，再帮助形成方法选择。例如先讨论样本中有哪些企业及其联系，再解释标准误的选择。
- 给出有依据的推荐，说明不同选择会改变什么。不能只罗列术语或要求学生自己决定所有参数。
- 在真实问题出现时解释概念，必要时使用小例子；不把完整计量课程作为开始研究的门槛。
- 学生已有明确合理选择时尊重其方向；发现问题时说明具体原因和可行修改。
- 研究可以反复返回问题与测量层面；记录修订理由，不能为了显著性静默改动设定。
- 讲解效果通过实际交流判断。可以邀请学生用自己的话描述关键选择，不把“答对问题”设置为完成操作的强制条件。

### 5.2 研究决定如何确认

用户确认应发生在已经形成可审阅选择之后。设计目标、变量与样本规则、基准模型、后续实质扩展沿用原标准的检查点；相关事项可一次解释并打包确认。

助手先展示具体方案、推荐理由、对研究问题的影响和剩余不确定性。用户对该方案说“按这个做”即可形成对话确认；Agent 记录方案标识及版本、用户原话、适用范围和依据位置。用户若在提出完整方案时已明确要求执行，不再重复确认。

姓名无法获知时记录为“当前用户（对话确认，未作身份认证）”，不编造真实姓名。依据位置指向实际保存的对话摘录或用户文件，保留记录性质，不称作平台认证。方案有多个版本、用户指代不明或拟执行内容超出已确认范围时才澄清。

纯讨论草案的同意不等于执行任意模型。技术性的路径修复、既定方案内重跑、制表等在已有授权范围内完成；新增变量定义、样本剔除、识别策略等实质变化需重新讨论。

### 5.3 缺失能力的交流方式

例如：“这两篇论文已经能帮助比较指标定义。当前没有可用的在线检索工具，关于是否存在后续研究还需要查证；先把已经读到的证据和待查问题整理出来。”

计算环境缺失时先完成适合当前阶段的研究工作。需要安装依赖或调用外部服务时说明用途，遵循用户及宿主的授权规则。读取本地材料的范围按任务确定；不自动上传完整数据库、发送邮件或投稿。

### 5.4 三个完整的经管指导示例

以下均为设计教学情境，涉及字段、样本数和估计值均是假设输入，用于说明交互和检查要求，不是本仓库已完成的真实研究。实施时以测试材料或用户实际文件替换，不将教学数值登记为真实结果。

#### 示例 A：从模糊方向到候选方案

**用户起点：** “想研究企业数字化与经营风险，有企业年度数据，但不知道怎么设计。”

| 环节 | Agent 的具体工作 | 学生获得的帮助与产物 |
| --- | --- | --- |
| 澄清现象 | 了解为何关心这一关系、风险指什么；已有材料先读，不要求直接选模型 | 将兴趣缩小到可以讨论的经营现象 |
| 阅读材料 | 本情境假设数据含企业、年份、数字化指标与年度利润率；先核实指标定义、年份覆盖及原始缺失含义 | 材料清单；明确利润率水平不能直接充当利润波动 |
| 核查测量 | 阅读用户提供的指标依据，讨论跨期波动的窗口、时间顺序与可用年份；不足之处记录待核实 | 文献证据卡、指标构造建议及其样本代价 |
| 形成方案 | 提出“经营波动在现有企业年度中怎样分布和变化”与“数字化与企业内经营波动变化有何条件关联”两条路线；后者取决于测量及可用变化检查 | 两个问题的区别、共同数据需求、关联分析尚需的控制条件与推断选择 |
| 提供推荐 | 说明先核实测量和构造样本，再用描述帮助理解数据；描述结果不能代替关联问题，也不自动视为稳健性 | 带理由的下一步，不按预期显著性选择路线 |
| 记录和交接 | 用户理解并确认测量、样本与具体分析选择后，登记对应版本，交 analysis 执行 | 可读方案和确认范围；学生能说明模型在比较什么 |

该例展示完整的准备路径，不保证每个方向都产生同样两条方案。实际只支持一条或没有可行方案时，保留原问题并给出最小补充需求。

#### 示例 B：从样本流失到处理决定

**用户起点：** “加入控制变量后样本少了很多，是不是直接用剩下的数据？”

本情境假设初始数据有 1,000 行，主变量共同可用 920 行，加入拟议控制变量后共同可用 700 行；这些数值仅为演示。

1. **先查事实：** Agent 读取盘点、方案和实际缺失统计，确认新增 220 行流失是否确由控制变量缺失导致，并查看流失集中在哪些企业或年份。示例中的计数不能直接替代工具计算。
2. **解释影响：** 用当前数据说明，比较两次系数时同时改变了控制条件与样本，变化不能全部归因于控制变量。
3. **提出可审阅选择：** 说明每个控制变量的研究角色、能否补齐数据，以及是否在相同的 700 行上比较不同设定以区分来源；不自动删掉缺失多的控制变量。
4. **确认后执行：** 样本和分析变更超出现有授权时取得确认，再运行并核对。原始缺失状态保留，未披露不变成零；保存所有运行及其用途。
5. **形成交付：** 样本变化表、处理理由、同样本比较结果和解释范围。若数据不足以判断选择性流失，则明确未解决问题，而不是把完成案例分析当成已解决偏差。

#### 示例 C：从不显著结果到合理解释

**用户起点：** “结果不显著，是不是论文做不下去了？”

本情境假设已核对的教学结果为：数字化指数提高 1 单位，对应利润率波动的条件关联估计为 −0.02 个百分点，95% 置信区间为 [−0.08, 0.04] 个百分点。真实任务必须读取实际结果，不能套用这些数值。

1. **先核对：** 确认模型、样本、单位、区间和数据质量，检查这是否为当前有效结果；不先安慰或先推荐换模型。
2. **解释证据：** 点估计方向为负，但区间仍涵盖正、负及零附近的关联。是否足以排除有实际意义的幅度，还要结合研究背景判断；当前不能直接得出“没有关系”。
3. **帮助诊断：** 查看测量质量、样本信息量和可用变化，区分执行问题与估计不精确。若计算正确，也应如实接受证据暂不明确这一研究结果。
4. **建议下一步：** 优先完成事前计划中有依据的检查；新增指标或设定需说明针对的问题，并保留为结果后的探索。不会默认遍历指标、样本或模型寻找显著性。
5. **形成交付：** 判断—证据表和与实际结果一致的说明；共同决定继续补证据、收窄问题或暂停某条路线。学生理解“未得到明确支持”与“研究毫无价值”的区别。

```text
        ├── literature/             文献资料与文献证据

        │   ├── notes/              阅读笔记和文献证据卡
        │   └── evidence/           研究判断与来源的对应关系
        ├── data/                   数据来源、处理和样本
        │   ├── raw/                按来源与批次保留的原始数据
        │   ├── interim/            需要保留的处理中间产物
        │   ├── processed/          按数据版本区分的分析样本
        │   └── metadata/           字段字典、来源、缺失规则和校验信息
        └── research/               研究设计、执行、表达与项目记录
            ├── plans/              候选方案和具体分析计划
            ├── tasks/              持续研究任务及其状态
            ├── decisions/          研究决定与实际确认依据
            ├── sessions/           对话工作摘要及关键可见摘录
            ├── code/               正在编辑的项目脚本
            ├── runs/               各次运行的代码快照、环境、日志和结果
            ├── reports/            审计、图表及结果解释
            ├── drafts/             按需形成的论文段落和研究汇报
            └── history/            材料旧版、项目检查点及其清单
```

当前维护目录无需建立上述个人研究目录。产品负责提供生成和管理这些目录的能力及模板，具体目录由用户使用时创建。

每项新研究建立 `literature / data / research` 三个主目录，内部子目录按材料和任务需要创建。所有 Skills 使用同一套项目路径登记，research 负责协调，evidence 管理文献内容，analysis 管理数据和运行，design/interpret 管理相应研究产物。目录名称不代表对应一个新的独立 Skill。

以上均为单项研究目录内的路径。多个研究项目各自拥有完整目录和独立标识，不能混用数据或方案。用户已有自己的文献、数据和研究目录时先登记路径映射，不为了统一名称立即移动文件；整理、移动后需要更新引用并检查可访问性。

v0.2 提出的 `notes/`、`plans/`、`runs/`、`reports/` 等顶层路径在新项目中按上述结构归位；文献笔记与对话/决定分别存放。已有项目保持原路径可读，通过明确的迁移记录逐项更新，不重建或覆盖历史。`research_state.json` 与根目录进度视图的位置保持兼容。

各 Skill 只增加确有用途的 `references/`、`scripts/` 或 `assets/`，不为目录完整而建立空文件。共用研究原则只维护一份，专项方法按需读取。

### 6.2 状态与可读材料的关系

复用现有 `research_state.json`，不另建一套 YAML 状态。待扩展的对话接续、文献证据和概念草案作为有约定结构的产物登记，保留现有版本与依赖机制。

`研究进展.md` 是可再生成的阅读视图，显示研究问题、当前方案、已完成内容、未解决问题、关键决定和下一步。它不是判断某结果已通过验证的权威来源。用户直接修改该文件时，Agent 对照状态核实变化，将实质修改作为新输入登记，再更新视图。

保存顺序为：先保存产物文件及校验信息 → 经校验保存状态引用 → 更新阅读视图。中断后未被状态引用的文件只能作为待核对材料；视图更新失败可从有效状态重建。首次支持此链路时需加入中断恢复测试。

Agent 通过受控的本地工具操作状态，避免直接重写整个 JSON。工具要检查方案确认、依赖版本、原始文件变化和运行结果，并返回实际保存凭据。共享指令提供行为指导；它们本身不构成防篡改系统或不可绕过的执行边界。

### 6.3 需要保存的接续信息

**保存面向科研工作的对话记忆，而不是假定能完整导出宿主聊天历史。** Agent 将当前可见对话中影响研究的内容写入项目记录，下次会话或另一个 Agent 读取这些文件即可接续；不依赖账号级长期记忆自动迁移。

- 当前研究目标、用户已明确的背景与约束；不推断或保存无关个人信息。
- 字段含义、材料来源和已核实程度，区分用户提供、原文证据、程序计算和 Agent 建议。
- 正在讨论或已确认的方案版本，以及未解决的研究问题。
- 实际执行、失败、核对和产物位置；保留看到结果后新增分析的原因。
- 下一步建议与理由，以及哪些动作已获授权。

不保存模型隐藏推理。研究依据写成可供用户核对的简明理由。

每次任务收尾，进度视图还显示：本轮实际使用了哪些输入、哪些关键材料尚未获得、完成了哪些检查、形成哪些文件。该记录服务于续接和证据核对，不要求每轮罗列全部技能或反复输出检查清单。

**保存时机与内容：**

- 重要事实更正、研究选择或明确确认出现后，及时保存原意、来源与适用版本；不能等到整项分析结束才记录。
- 一个实质工作单元结束或切换任务前，在 `research/sessions/` 写工作摘要，保存实际产物、未解决问题、下一步和已获授权范围，并更新状态与进度视图。
- 宿主提供可访问的消息标识时可引用；否则保存当前可见的必要摘录及本地记录时间，不编造会话编号。来源不足时标为用户说明或待核实，不能凭摘要变成已验证事实。
- 完整逐字对话归档仅在用户要求且宿主支持导出或用户提供记录时处理。未保存的内容、不可访问的旧会话和突然中断前尚未写入的信息不承诺恢复。

恢复时先读进度概览，再按当前任务读取相应会话摘要、决定和有效产物；检查实际文件与版本。摘要与当前事实冲突时保留原记录、登记更正，不能按旧摘要直接重用已过期结果。

### 6.4 用户材料与多项目

用户可以把材料放进项目，或指向已授权的其他目录。Agent 先登记来源；原始数据保持原样，转换格式和构造变量形成新产物。`research-projects/` 排除在本工具仓库的 Git 提交之外；各项研究自己的本地版本与可选 Git 管理见第 6.6 节。发布工具前检查未混入真实研究材料或凭据。

一个克隆可以保存多项研究，入口负责明确当前项目。首版以同一时刻一个 Agent 写入一个研究项目为使用条件；宿主切换前结束上次写入。后续若要支持并发编辑，需要增加锁或事务机制。

换电脑后源文件路径可能变化：通过材料索引重新定位并校验内容；无法匹配时要求补齐材料，不能只凭旧状态宣称可复现。第一版不承诺自动同步或备份。

### 6.5 六类可复用研究模板

模板由 Agent 根据已读材料填写和更新，学生阅读、讨论研究选择。未知信息明确保留；不会为了填满模板而虚构字段、证据、确认或结果。

| 模板及维护 Skill | 使用时机 | 必填信息 | 项目中的交付位置 |
| --- | --- | --- | --- |
| 研究任务卡：research | 综合材料、形成/修改方案、执行分析、交付结果说明前 | 要解决的问题及理由、输入与版本、相关方案及已有授权、所需能力、预期输出、检查方法、仍缺信息；结束时回写实际产物和检查 | `research/tasks/`，状态中登记引用 |
| 文献证据卡与判断—来源表：evidence | 来源开始影响研究判断时 | 来源标识与定位、已读范围、研究对象/方法、可用发现、所支持的具体判断、支持性质及边界、尚需查证的内容 | `literature/notes/` 与 `literature/evidence/`；一份来源可关联多项明确判断 |
| 候选方案比较：design | 讨论研究路线或实质设计变更时 | 问题与目标、理论/测量依据、实际字段或缺口、样本与比较方式、条件、可行性、与其他方案关系、优先级理由 | `research/plans/`；正式方案另绑定结构化记录 |
| 分析任务与表图规划：analysis | 正式执行前 | 每项分析回答什么判断、计划和数据版本、模型/样本/变量选项、拟输出结果字段、图表目的及数据来源、独立核对方法 | `research/plans/`；与任务卡互相引用，不重复确认 |
| 判断—结果证据表：interpret | 有结果需要解释或比较时 | 事前判断、方案与运行标识、实际样本、估计量和区间、单位、诊断、支持程度及理由、解释范围、下一步 | `research/reports/`；明确引用实际结构化结果 |
| 研究进展概览：research | 实质任务结束或恢复时 | 当前问题、有效方案、完成内容、所用/缺失材料、未解决事项、实际文件、下一步与授权范围 | `研究进展.md`，从状态重建 |

模板源分别放在所属 Skill 的 `assets/` 中，平台副本随 Skill 同步。字段含义和记录约定放在共用研究手册；文献或结果修订时，用标识和版本更新引用，不复制出彼此矛盾的多份事实。

**任务卡的精简填写示例（教学示意）：**

| 字段 | 内容示意 |
| --- | --- |
| 本轮问题与理由 | 判断控制变量缺失造成的样本变化是否影响两次估计的比较 |
| 输入与授权 | 引用当前方案、两次实际运行和字段说明的真实标识；先读取与检查，新增分析沿第 5.2 节确认规则处理 |
| 预期交付 | 样本变化说明；必要时形成同样本比较提案 |
| 检查方法 | 对照两次样本标识、逐项核查缺失原因；检查是否还改变了变量或模型 |
| 收尾记录 | 填入实际读取文件、输出位置、检查结果及未解决事项；不能预先写“通过” |

表图规划先定义用途和所需结果字段，不预先填入“应当显著”的系数或星号。教学图形如使用合成数值，应与真实项目结果隔离并明确标注。正式说明中的每个表格单元格和图形系列，都应能追溯到对应运行或实际描述统计产物。

这些模板是项目记录的可读形式，沿用第 6.2 节的状态与产物约定，不形成另一套并行审批或权威状态。

### 6.6 版本管理：文件可找回，结果能追溯

**三个目录属于同一项研究，共用一条有依赖关系的版本记录。** 用户可以说“保存这一版”“比较老师修改前后”“继续上次分析”或“恢复之前的方案”，由 Agent 处理路径、版本和关联检查，无需学生维护版本编号。

默认本地版本管理包含两部分：状态登记版本及其依赖，同时保存对应的实际文件。只记录文件名或校验值不能找回被覆盖的旧内容，因此被登记的版本必须有可访问的内容副本或明确保留的原始来源。

| 材料 | 保存方式 | 修改后的处理 |
| --- | --- | --- |
| 文献原文与笔记 | 原文按来源登记；笔记和证据表保留修订版及来源定位 | 更新引用；若关键证据或解释变化，核查依赖它的方案和文字 |
| 原始数据 | `data/raw/` 按来源和获取批次保留；新导出另存 | 重新盘点，不能覆盖旧批次后继续使用旧校验记录 |
| 处理后数据 | `data/processed/` 按版本保存，关联输入、处理脚本、样本及字段说明 | 新处理产生新版本，关联分析和报告需重新判断有效性 |
| 方案、决定与稿件 | 保留当前工作文件；已登记旧版保存在 `research/history/` 或各自产物版本目录 | 说明更改理由，保留旧方案、确认范围及结果后探索记录 |
| 代码、运行与报告 | 工作代码放在 `research/code/`；每次执行在 `research/runs/<运行标识>/` 固定代码快照、环境、日志和结果；报告引用相应运行 | 修复或重跑使用新运行标识；旧运行和对应报告仍可查阅 |

**保存检查点。** 实质任务完成、方案确认或用户要求保存某版时，在 `research/history/` 登记一个项目检查点，列出当时的文献、数据、方案、运行和报告版本，并保留当时的状态快照。大文件按内容版本保留一次，检查点引用它们；不在每个检查点重复复制整套原始数据。外部材料未纳入本地保留时，清单注明恢复依赖其持续可访问，不能仅凭校验值宣称已备份。

**比较和恢复。** 对比应说明研究问题、测量、样本或结果发生了什么变化。恢复旧方案产生新的当前修订，保留之后的历史；重新检查其输入是否可用、授权是否适用及下游依赖，不直接覆盖整个旧状态来抹去后续研究，也不自动把旧结果标成当前已核对。保存沿第 6.2 节顺序进行；中断后以最近有效保存为准，孤立文件先核对再登记。

**Git 是可选的辅助方式。** 默认本地历史无需 Git 即可使用；用户要求启用后，可为每项研究建立一个独立的本地 Git 仓库，三个目录共同管理。研究仓库优先跟踪代码、文字、元数据和版本清单，原始/大体积数据、论文原文及凭据按项目排除规则处理，保留方式仍由上述材料索引说明。Git 提交不能替代样本、参数和数值检查。

启用时确定跟踪范围和按任务或里程碑提交的偏好；之后 Agent 在该范围内提交，无需逐次再问。提交前只选本任务文件，不把用户其他改动一并提交；没有可用 Git 身份时不编造或修改全局身份，本地研究历史继续工作。联网备份、推送或公开发布需要相应请求与授权，不由“保存这一版”隐含触发。

若在研究子目录启用独立 Git，Agent 仍从工具仓库根目录打开项目，研究 Git 操作明确指向该子目录。单独打开研究子仓库可能改变入口和 Skill 的发现范围，需要另做入口适配并验证，首版不承诺自动继承父目录全部能力。

### 6.7 持续项目管理：围绕下一步推进

统一入口同时承担轻量项目管理。用户无需另开一个管理界面，可以直接说“整理这些论文”“看现在还缺什么”“按老师意见修改”“比较两版结果”“继续下一步”。

- **组织材料：** 新材料进入登记过的目录，记录来源和用途；先检查已有内容，减少重复导入。改名或移动时更新相关引用，不能只整理外观而断开来源。
- **维护任务：** 对需要跨会话推进的工作，在 `research/tasks/` 登记目标、输入版本、依赖、优先级、下一步及实际产物。状态区分待开展、进行中、等待材料/决定、待核对、已完成；状态名在工具实现时统一映射。
- **安排顺序：** 根据当前问题和依赖给出最值得推进的下一步。已有授权的工作继续执行；等待资料时，保留阻塞原因并推进独立工作，不把等待状态当作全部任务完成。
- **吸收反馈：** 老师意见进入决定与任务记录，说明哪些方案、数据处理和文字受影响，保留修改前版本，并检查修改后的对应关系。
- **报告进展：** `研究进展.md` 显示目前做到哪里、有效成果、未解决事项及下一步。只在用户需要时展开完整任务和版本清单；用可核实产物判断完成，不编造完成百分比。

例如，用户说“老师建议换一个风险指标，原来的结果也留下”：入口读取现有方案与反馈，design 解释测量变化，analysis 核实数据可用性；在明确的新方案与授权下生成新数据版本和运行，再由 interpret 比较两条路线。原方案、原结果和更改理由全部保留，新报告引用各自实际使用的材料。

第一版的持续管理发生在用户与 Agent 工作的过程中。保存任务与截止日期不等于后台自动运行或到时提醒；无人打开会话时的自动推进另行设计，不计入本次范围。

## 7. 工具适配：复用哪些，补齐哪些

### 7.1 最小工具契约

工具由 Agent 调用，可以使用仓库内 Python 接口或内部脚本。下表列职责，不预先指定一组新的用户命令。

| 工具职责 | 输入 | 输出/核验 |
| --- | --- | --- |
| 检查能力与打开项目 | 项目路径、当前任务所需能力 | 只报告实际可用能力、项目状态和相关阻塞；无自动安装副作用 |
| 读取和盘点材料 | 指定文件、主体/期间/数值字段及来源说明 | 文件标识与校验值、结构和缺失事实、可读审计 |
| 保存研究讨论和文献证据 | 内容、来源、未知项、引用关系 | 有版本的记录；格式检查与证据是否充分分开 |
| 登记/修订方案 | LLM 整理的方案、数据及文献引用 | 字段/样本/方法契约检查，旧版本保留；修改后下游过期 |
| 记录具体决定 | 方案版本、用户明确意见、实际依据位置 | 决定记录，约束本次执行范围 |
| 执行与核对 | 已确认方案、有效数据、固定工具或登记的项目脚本 | 实际运行参数、代码与环境、结果、警告及独立核对；不同代码路径均检查授权、支持范围和版本 |
| 管理目录与材料位置 | 项目标识、实际路径、来源和已有布局 | 路径映射；改名/迁移后引用仍有效，多个项目互不混用 |
| 保存进展与恢复 | 可见对话中的重要事实/决定、有效状态和产物引用 | 可追溯摘要、可读概览、下一步及中断/过期说明 |
| 保存、比较与恢复版本 | 当前产物、旧版内容、依赖和更改理由 | 不可静默覆盖的文件版本、检查点清单、差异与影响；恢复形成新修订 |
| 更新持续任务 | 目标、输入版本、依赖、下一步和实际产物 | 可核实任务状态；上游改变后重新检查完成条件 |

### 7.2 需要特别补齐的接口缺口

现有 `register_plan()` 只绑定一个数据盘点，尚未将支持方案的文献或研究讨论显式加入依赖。接入 Agent 方案时须增加这些引用，并区分“资料已记录”“内容已核实”“方案已确认”。

没有数据的早期方案保存为研究讨论或概念草案，不强行通过现有可执行方案校验，不虚构盘点或字段。原始文件变化或上游定义修改时，消费前检查版本；不能通过把状态手动改成通过来继续使用。

现有 `candidates.py` 对结果后探索的追踪不能只留在模板入口。新增的 Agent 方案登记与修订路径也必须检查已有结果历史，确保换入口后仍保留探索性质与原因。

现有状态版本不能直接视为所有材料的完整历史副本。需要补齐实际文件快照、项目检查点、目录映射、对话摘要和持续任务契约；对读取旧布局、保存中断、外部文件改变、恢复旧版后依赖更新分别验证。可读任务卡与状态中的任务记录使用同一标识，避免两个清单各自更新。可选 Git 只作为这些记录的辅助，不成为保存进度的前置依赖。

### 7.3 数据格式与估计后端

当前工具实际只审计 UTF-8 CSV。第一版应让 Agent 识别用户常见的 Excel/CSV 材料；Excel 读取/转换需要新增并验证适配，记录工作表、表头、类型和原始文件对应关系，转换不能把文本代码或缺失标记悄悄改变。其他格式按已验证工具能力处理。

正式计算先支持一条 Python 统计执行路线，即选定并核验实际估计实现、样本处理和结果读取方式。这里的“执行后端”不要求先开发覆盖所有科研操作的通用回归平台：可以在这条路线内由 Agent 生成某项研究所需的处理、分析和制图脚本，再用公共契约检查。

用户已有 Stata 代码或其他结果可以阅读讨论，但在相应执行和核对链未支持前，不将其标记为本项目已复现结果。具体统计实现与参考核对在实施计划中明确；当前并未因设计增加了代码生成路径而获得新的已验证估计能力。

### 7.4 固定工具与 Agent 生成脚本的分工

| 工作 | 优先方式 | 原因 |
| --- | --- | --- |
| 输入标识、重复键/缺失检查、版本依赖、确认和运行登记 | 固定工具 | 保持检查规则一致，避免每项研究重写基础逻辑 |
| 项目特有的字段映射、变量构造、样本处理、分析调用和图形 | Agent 按方案生成脚本，复用已有计算实现 | 适应真实研究差异，减少先造通用平台的等待 |
| 结果读取、表文一致性、关键数值和样本核对 | 固定核验接口 + 针对该分析的独立参考 | 生成代码可能出错，需要核对实际执行与结果 |

**生成脚本的执行约定：**

1. **先绑定计划。** 读取有效方案及确认范围，记录输入版本、数据口径、预期模型和样本处理。数据盘点与技术检查可按其任务授权进行，正式估计必须通过方案执行关口。
2. **先保存代码。** 工作脚本保存在 `research/code/`，执行前将具体代码快照固定到 `research/runs/<运行标识>/`，记录代码版本或校验值、依赖版本及执行入口；结果生成后不能静默改写同一运行的代码或日志。修复保留前次运行记录。
3. **控制读写范围。** 使用任务指定材料，原始数据保持原样，转换和分析样本另存。安装、联网等遵循已有授权与宿主权限；运行失败不成为擅自更换模型、删样本的理由。
4. **实际运行并登记。** 保存实际样本标识、观测数、模型/固定效应/标准误选项、环境、警告、日志和结构化输出。关口应比较实际执行记录与方案；不能仅采信 Agent 在任务卡上填写的“已按方案执行”。
5. **完成数值核验。** 检查结果有限性、样本链、单位和区间；首次实现或更换实现路径时，对关键结果使用独立参考计算，并按事先确定的数值容差比较。说明参考来源和检查覆盖范围。
6. **核验后交付。** 结果解释和正式表图消费已经核对且未过期的产物；尚未核对的输出标为待检查。改变实质研究设定时形成新方案或修订，并保持结果后探索记录。

代码保存、实际运行、核验通过是三个不同状态。若现有工具暂不能登记并核对某种脚本结果，该脚本可以作为待接入的分析草稿，不能通过手改状态进入正式结果链。生成代码也不扩大首版方法范围。

### 7.5 两类交付检查

每项带研究产物的任务根据其内容进行两类检查，由当前 Agent 与可用程序完成；不要求额外启动代理或增加用户确认。

| 检查 | 核心问题 | 证据示例 |
| --- | --- | --- |
| 任务和执行一致性 | 是否回答了本轮问题，是否使用指定输入与已确认版本，实际操作是否偏离方案，产物是否齐全 | 输入校验、任务卡与实际运行对照、错误日志、结果引用 |
| 研究证据与解释质量 | 文献是否支持具体主张，数值是否正确，样本与比较是否解释清楚，结论是否超出证据 | 原文定位、独立数值核对、判断—证据表、样本变化说明 |

检查脚本可以识别缺少文件、残留占位、模拟值误用等问题，但字数、引用标记数量、表格是否存在都不能证明研究正确。自动可验证的计算交给程序，方法假设与文献解释保留论据及未解决问题。

工作计划、教学解释和正式写作分别保存在相应位置。需要成稿时核对其与研究记录一致，不把操作要求、等待确认的意见或教学数据写成研究结论。

- 本机缺少 Python 或检索工具时，可以开始相应范围内的研究讨论，准确说明后续所需条件。

### 10.2 代表性研究场景

| 场景 | 必须观察到的行为 |
| --- | --- |
| “只有数字化与风险这个想法” | 围绕现象追问，帮助具体化；不要求先填完整变量和模型表 |
| 数据列名含义不清 | 阅读现有说明、指出具体疑点；不以列名猜测替代核实 |
| 只有一条路线可行 | 给出依据和补充选项，保留原问题，不强凑三条 |
| 论文只有摘要可读 | 限定引用范围，不生成正文页码或声称完成全文核验 |
| 学生不知道如何选择模型 | 给出推荐、解释比较逻辑和条件；不用“请选择模型”把判断直接推回学生 |
| 重复键、合并扩行、缺失与零混淆 | 工具检出并保存证据，解释研究影响，停止依赖错误数据的执行 |
| 模型实际参数与确认方案不同 | 检出差异，保留日志，不作为已按方案完成的结果 |
| 固定效应吸收 X 或估计数值错误 | 不生成虚假系数和正式结论，说明需要处理什么 |
| 结果不显著或多方案方向不同 | 比较效应量、区间、样本和设定；保留全部结果，不自动搜显著性 |
| 看到结果后提出新方案 | Agent 新入口同样保存探索标记、提出时间和原因 |
| 用户改了变量定义 | 旧结果和文字过期，确认受影响步骤并正确重跑 |
| 意外中断后继续 | 从有效状态恢复，不以孤立文件或旧概览推断完成 |
| 用户要求修复本仓库代码 | 进入开发任务，不创建研究项目或启动研究接待 |

每个宿主使用同一组预先定义的输入材料，保存实际对话、工具调用和产物。平台差异允许体现在措辞和工具选择上，关键研究行为必须一致。计算结果以独立参考及预先定义的容差核对。

Agent 行为评价检查实际是否读到证据、是否提出合理问题、是否保留未知和研究边界，不以匹配固定句子作为通过标准。严重问题修复后对相关场景重新验证。

### 10.3 学生体验验收

建议邀请至少 3 名目标初学者完成短任务，用于发现可用性问题，不据此宣称普遍教学有效。观察他们能否：

1. 从自然语言开始，无需自行选择 Skill 或编写参数；
2. 说清正在回答什么问题、为什么选择当前指标和比较方式；
3. 理解一个真实的样本变化或结果不确定性；
4. 找到输出，并在新会话继续研究。

记录卡住的位置、误解和需要人工提示的次数，据此修改入口和指导内容。程序测试通过不能替代这项检查。

| --- | --- |
| 五个 Skills 有实际操作规程 | 用第 5.4 节场景及变体检验：实际读取材料、解释选择并形成可检查产物，而非仅输出步骤清单 |
| 任务卡适度使用 | 综合文献或执行回归时有输入输出与检查记录；普通概念问答不额外要求学生填卡或重复确认 |
| 文献驱动研究判断 | 对给定支持、间接支持和相反证据，能定位来源并说明差别；不存在的文献/字段保持未知 |
| 分析与表图预先对应 | 执行前说明每项输出回答什么问题；执行后来源能追溯，原方案和全部实际运行保留 |
| 项目脚本真正可复现 | 在固定教学数据上执行已登记代码，核对实际样本和数值；重跑结果在预定容差内一致 |
| 生成代码错误会被识别 | 注入错误连接、单位变换或模型选项偏离，独立核验能发现；写了“验证通过”不能绕过检查 |
| 模拟材料不进入真实结论 | 教学输入与真实运行分开；未执行、未核对和过期输出均不能成为正式结论依据 |
| 两类检查各有证据 | 既有任务/执行对照，也有来源或数值核对；仅靠字数、标题、引用标记计数不能通过研究验收 |
| 进度能够支持换 Agent 接续 | 下一宿主读到有效记录，能识别缺失输入、实际产物及下一步，无需重新询问已记录事实 |

案例中的预期行为是验收依据，示例措辞和虚构数值不是固定答案。正式验证使用独立准备的测试材料及参考结果，并记录失败与修订。

### 10.5 自动路由、记忆与项目管理验收

| 场景 | 必须观察到的行为 |
| --- | --- |
| 自然语言提出文献、数据、结果或反馈任务 | 按意图与现有材料选择相关 Skill；跨阶段任务可顺序调用，无需用户记住名称 |
| 用户明确指定某 Skill；或自然语言匹配失误 | 尊重明确选择并检查前提；缺少能力如实说明，路由错误能根据反馈纠正，不宣称从不误选 |
| 用户更正变量含义后结束会话 | 新会话读到更正及来源，旧记录保留；引用旧定义的方案/结果被识别为待复核 |
| 从 Codex 顺序切换至 Claude Code | 读到关键讨论、当前方案、实际产物和下一步，不要求重新陈述已保存事实，不虚构完整聊天历史 |
| 保存时中断，或只有旧进度概览 | 以有效状态及可核对产物恢复；孤立文件不自动算完成，概览可重建 |
| 新建研究或接手用户既有目录 | 新项目形成三个主目录，旧目录保持可读并登记映射；整理后引用有效，不生成重复项目 |
| 原始数据被外部覆盖，或旧版文件缺失 | 消费前检出变化并标明影响；校验值不能替代丢失内容，不再宣称该版可恢复 |
| 比较两个项目检查点 | 能列明各自文献、数据、方案、脚本和报告版本，并解释研究上的差异 |
| 恢复旧方案，再继续分析 | 形成新的当前修订，保留之后的历史与探索标记，重新检查数据、授权和结果依赖 |
| 同时保存两项研究 | 任务、记忆、版本和产物互相隔离；“继续研究”指代不明时先定位项目 |
| 任务缺材料或上游发生变化 | 状态反映等待或待核对；下一步有依据，不仅凭已有文件就维持已完成 |
| 不安装/不启用 Git | 本地文件版本、检查点和恢复正常工作；明确本地保存未自动远程备份 |
| 用户启用单项研究 Git | 只跟踪约定文件，工具仓库仍排除研究目录；不夹带其他修改、不自行推送；从工具根目录继续研究时入口可用 |
| 维护者讨论或修改研究功能 | 处理产品设计/开发，不因出现研究术语而创建真实研究目录；测试使用临时项目，发布包包含工具与模板 |

验收同时检查实际落盘内容与 Agent 的表述。“已保存”“已完成”“可以恢复”均需对应可读文件及检查结果。第一版不以后台自动提醒或多 Agent 同时写入作为通过条件。

## 11. 请审阅的六项设计选择

| 选择 | 本稿建议 | 对体验的影响 |
| --- | --- | --- |
| 使用方式 | clone 后在 Agent 中打开项目，自然语言开始 | 不建设独立用户界面，集中验证研究指导 |
| 首版宿主 | Codex + Claude Code | 两套入口同一内容，以实测声明兼容 |
| Skills 组织 | 一个统一入口 + 四个专项 Skills，根据自然语言、进度和材料自动选择，允许用户明确指定 | 保持连续对话，无需学生自行判断技能名称 |
| 指导风格 | 推荐与执行结合，在当前研究中解释理由 | 学生不必先懂全部方法，同时能逐步形成判断 |
| 科研记忆与项目管理 | 每项研究用三个主目录，保存重要对话、任务、实际文件版本和关联检查点；Git 可选 | 下次能接着做、比较或恢复旧版，保留文献到结果的依据 |
| 发布范围 | 先交付阶段 A 试用，阶段 B 用固定工具与经核验的项目脚本完成闭环 | 明确完成边界，避免先建设通用平台才开始研究 |

用户可以直接对具体章节或表格提出修改。阶段 A 的任务顺序、文件、接口及验收已整理到[实施计划](../plans/2026-09-15-agent-entry-skills-implementation.md)，后续从保存当前开发基线开始执行；可加载的入口与 Skills 仍待实施。
