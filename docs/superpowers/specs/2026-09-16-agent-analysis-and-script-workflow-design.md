# Agent 分析判断、常见数据处理与项目脚本工作流

日期：2026-09-16。代码基线：开发分支 3a19da3（0.2.0a2）。

状态：需求及自动化原则已确认；第一批已在开发分支实现并完成验收，见 [验收记录](../../agent-analysis-validation.md)。第二批通用方法核验仍为后续扩展。main/ZIP 未随本次开发提交发布。

## 1. 已确认的目标

用户希望 Agent 能根据研究问题和实际数据判断适合采用什么分析，完成缩尾、取对数等常见处理，自动编写 Python 或 Stata 脚本，使研究者无需承担繁琐的编程工作。

用户选择的自动化方式：先给出简短的“模型＋数据处理方案”，在已有授权内自动写脚本、运行、检查和修复技术错误；改变变量含义、样本或识别策略且超出既有授权时，才请研究者决定。已确认的规则不逐步重复询问，也不要求用户填写机器配置或选择统计库。

本方案恢复并扩展原入口设计第 7.4 节“固定工具＋Agent 生成项目脚本”的分工。内置估计器的覆盖范围不应成为整个 Agent 思考、编程和分析的能力上限；具体分析是否已经执行、核验到什么程度，仍依实际证据判断。

## 2. 当前实现与缺口

| 当前代码 | 已有能力 | 需要补齐 |
| --- | --- | --- |
| design / analysis Skills | 读研究问题、字段说明、方案及授权；提出候选设计 | 把方法选择、处理建议、项目脚本和执行检查明确串起来 |
| candidates.py | 固定规则产生描述或固定效应讨论草案 | 作为数据事实辅助工具，不冒充研究方法推荐器；因果请求不能只得到范围提示后结束 |
| execution_spec.py | 显式筛选、完整案例、企业年度键和样本链 | 变量变换、缩尾、合并、滞后与数据处理版本 |
| execution.py / run_worker.py | Python / 可选 Stata 的描述统计、固定效应及独立复核 | Agent 编写的项目脚本的登记、实际执行、技术修复及结果核对 |
| result_report.py / state.py | 已核验结果的报告、过期检查和恢复 | 区分脚本执行记录与方法核验，避免将自定义脚本退出成功标成数值通过 |

现在生成的 run.py 是冻结工具入口，Stata do-file 是有界估计器产物；它们尚不等于按某项研究完整编排的“数据处理—回归—诊断—出表”代码。

## 3. 三种实现方式及建议

| 方式 | 优点 | 代价 |
| --- | --- | --- |
| **Agent 研究判断＋项目脚本＋复用核验工具（推荐）** | 能适应不同研究，用户交代研究需求即可；已有执行与复核基础继续复用 | 需要把脚本、样本、结果和核验的关联做好 |
| 逐个方法全部封装后再开放 | 每个固定入口边界清晰 | 方法和组合扩展慢，难以覆盖实际变量构造与特殊设定 |
| 只让 Agent 自由写代码并运行 | 起步快、灵活 | 容易缺少版本、失败记录、实际样本核对和独立检查 |

采用第一种。项目代码由宿主 Agent 根据方案生成；工具提供数据事实、常用处理、文件记录、运行和核验。不开辟新的模型 API、网页产品或默认多 Agent 系统。

## 4. 学生看到的使用流程

1. 用户提供研究方向或问题、数据位置，以及已有字段说明和论文依据。
2. Agent 读取实际数据：观察单位、横截面/面板结构、时间范围、结果变量性质、缺失、极值、重复键及可用变化；读取与选择有关的既有设计和证据。
3. 给出简短方案：准备回答什么、推荐什么模型、哪些变量如何处理、固定效应和标准误怎么设、为什么、还缺哪项会影响选择的信息。
4. 授权已覆盖就继续。只将尚未解决的实质选择交给用户；不要把 Python 包、函数参数、路径修复等技术细节推回给研究者。
5. 自动生成并保存脚本、运行、读取日志、修复技术错误、完成检查，生成可读表图与解释。
6. 交付处理后数据、完整代码、结果、处理记录和复核记录；继续研究时使用实际保存的版本。

用户可以说“按这篇论文的口径处理后做回归”或“帮我判断这个问题用什么方法”。Agent 负责核对论文口径能否用于当前数据，不需要用户先给出完整程序。

## 5. 如何判断采用什么回归

方法推荐综合研究目标、变量含义、比较对象、数据结构和识别依据。数据分布或显著性不能单独决定模型。先区分描述、关联、因果和预测；再判断结果变量性质、观察单位、可用变化、时间与处理安排、潜在内生性及误差相关结构。

分别记录四类选择，避免把它们当作互斥的“回归菜单”：

- 模型：连续结果的线性模型、二元结果模型、计数模型等。
- 识别或比较策略：固定效应条件比较、DID、IV 等，明确目标效应及额外依据。
- 估计设置：权重的来源、含义、类型和适用样本。
- 推断设置：传统/稳健标准误、聚类维度及相应理由。

通常给一个推荐方案和必要的替代方案，并分别标明：已由数据核实的条件、尚需解释的条件、缺失材料及其影响。没有足够识别依据时保留研究问题，说明可先完成的检查和补充证据，不把问题悄悄改成另一种问题。

DID 要核对处理发生时间、比较组及处理安排；分期处理和效应异质性需要相应方法，不能统一套一个双向固定效应交互项。IV 要有内生变量与工具变量的研究依据、相关性及识别论证，不从变量相关系数自动挑选工具。官方命令与诊断的依据见 [Stata DID 文档](https://www.stata.com/features/overview/difference-in-differences-DID-DDD/) 和 [ivregress 手册](https://www.stata.com/manuals/rivregress.pdf)。软件能计算并不代表识别假设已得到证明。

不得以“正态性没通过就取对数”、最大化显著性、遍历控制变量或批量替换样本作为默认方法选择机制。已有结果之后的实质修改保留探索历史；技术修错保持统计设定不变。

## 6. 常见数据处理

处理先形成可读规则，再编译为有顺序的步骤。原始数据不覆盖；每个新变量保存名称、来源、公式、单位变化及异常处理说明。

| 处理 | 必须明确的规则与检查 |
| --- | --- |
| 缩尾 | 字段、上下分位点、全样本或分组范围、阈值计算样本、分位数定义及步骤顺序；保存实际阈值和受影响数量。缩尾替换极值，截尾删除观测，不能混用。 |
| ln / ln(1+x) | 区分具体变换；先报告不满足定义域的观测及变量含义。不能因存在零就自动加 1，也不能把负数或缺失变成零。 |
| 比率、交互项、虚拟变量 | 公式、单位、分母为零、类别基准、缺失传播及目标字段；保留原变量。 |
| 标准化、中心化 | 用哪份样本估计均值/标准差，按整体还是组内；保存参数。预测任务的参数只能由训练数据拟合。 |
| 滞后、差分 | 实体键、时间频率和间隔；有年份缺口时不得把上一行当成上一年；防止跨企业串行。 |
| 合并、重塑、聚合 | 唯一键、预期一对一/多对一关系、聚合依据、未匹配和意外扩行；不静默去重或默认多对多合并。 |
| 筛选和缺失处理 | 继承已确认规则，逐步记录样本变化和原因，区分未披露、无法匹配与真实零。 |

处理规则按变量和研究目的确定，不对全部连续字段默认缩尾或取对数。先处理、后筛选，或先筛选、后计算缩尾阈值可能改变结果；顺序属于方案的一部分。遇到含义不明确的异常，继续完成独立可做的检查，集中提出一项实质选择。

常用处理提供可复用实现和对应 Python/Stata 代码生成；项目特有构造由 Agent 写脚本并附检查。两种语言对相同规则应核对观测键、缺失、处理阈值和实际数值，不能只比较总行数。

## 7. 自动编写、执行与修错

默认使用 Python；用户选择且环境支持时使用 Stata。没有 Stata 不影响 Python 完整流程。代码放在项目 research/code/，至少有处理入口、分析入口和一键运行入口；按实际需要组织文件，不为每次研究强造固定文件数。

脚本由 Agent 填入实际字段、路径、规则和依赖，无占位变量或需要研究者补写的主体代码。交付足够的注释和运行说明，可脱离原对话按记录环境重跑。生成代码与用户选择的引擎一致；不默认同时维护两份未核对的主分析代码。

执行前冻结代码、输入、方案和环境。每次尝试用新标识保存日志、输出、实际样本和运行状态；语法、路径、列名映射或 API 用法等技术问题可自动修复重跑。技术修复不能暗中改变取对数口径、删除样本、替换模型、权重或聚类方式。

执行使用已授权的项目材料与输出位置，使用现有进程生命周期保护。工作目录约束、代码阅读和文件登记不等于任意代码安全沙箱；文件系统、联网、安装和外部动作仍遵循宿主能力与用户授权。不会为运行项目脚本而扩大系统权限。

## 8. 项目脚本与独立核验

复用现有内置估计链完成其覆盖的方法。对于其他设计，不因缺少固定模型按钮就结束任务：Agent 核对实际环境和方法文档，形成项目实现及对应检查，再决定能够交付的执行和复核状态。

必须分别保存：

1. 脚本已生成：有代码，尚未证明实际运行。
2. 已执行：有真实进程、日志、样本及输出；记录哪些检查通过、哪些未完成。
3. 已独立数值核验：预定的独立计算和输出比较确实通过，且材料仍有效。

项目脚本运行不能通过自写一份“passed”JSON进入正式结果链。现有 result 的 completed/passed 门槛保持原意。新增项目脚本运行记录与结果接收接口，执行检查、处理核对、统计复核分开保存；报告分别展示覆盖范围。未完成统计复核的真实输出可以提供带状态的执行说明，不能标为正式已复核结果。

常见处理逐步独立计算阈值、变换、缺失和样本键；首次接入的估计方法用不同实现或可验证参考核对关键统计量，记录公式、自由度、协方差修正、容差和测试案例。不要求用户写验证程序。没有可用独立参考时，Agent 说明具体缺口并保留实际结果，不能声称普适核验已经完成。

自定义脚本已产生的系数、表或诊断即计入结果暴露历史；之后核验失败、改名或重跑都不能抹掉。数据处理、模型或环境变化需重新判断哪些产物失效，冻结历史包仍按自身源码和环境重跑。

## 9. 实施拆分

### 第一批：打通完整工作流

- 更新入口、design/analysis/interpret 指引，落实依据研究问题和数据选择方法、生成项目代码及最少必要确认。
- 增加版本化处理规则和常用处理：缩尾、ln/ln(1+x)、比率、交互项、虚拟变量、标准化、滞后/差分、显式筛选；复用现有导入、盘点和状态工具。
- 接通项目脚本登记、冻结、Python/可选 Stata 实际执行、技术修复记录和分项核验；建立有明确键关系的合并检查。
- 用当前已核验的描述统计和固定效应完成从原始数据到报告的完整验收；另用一个未内置的方法证明项目脚本流程能够生成、实际运行和如实呈现核验状态，不将其偷换成固定效应。

### 第二批：扩展常见方法的完整数值核验

沿同一工作流补齐线性 OLS、二元/计数模型、明确限定设计的 DID 和 IV，以及有明确语义的权重和多维聚类；每种方法分别规定数据要求、实现、参考算法、诊断和验收数据。优先级根据实际研究场景确定，不承诺任意方法组合已验证。

DID、IV、权重、多维聚类应成为 Agent 能分析和处理的研究需求，不作为永久拒绝清单；其实际执行与数值核验能力逐项用证据验收。

## 10. 验收场景

- 用户仅提供问题和数据，Agent 能定位真实字段和关键缺口，并给出带理由的推荐方案，而非只要求用户选模型。
- “按年对明确字段 1%/99% 缩尾后取 ln”：自动给出脚本、实际阈值、受影响观测、对数定义域检查、处理后数据及独立核对。
- 出现零、负数、重复企业年度键或断年：给出实际计数与影响，不偷偷改成 ln(1+x)、去重或按相邻行滞后。
- 用户已授权方案：连续完成处理、分析、检查和报告；故意注入路径/语法问题后能修复并保留失败尝试，不再次询问每个技术步骤。
- 用户提出 DID/IV：先检查对应研究与数据条件，再提出实现和诊断；缺关键识别信息时提具体问题，不用普通固定效应冒充。
- Python-only 环境完成完整流程，能读已有 Stata 产物；真实 Stata 环境另行验证生成 do-file、实际样本及关键数值。
- 旧脚本、旧结果或自报核验状态不能误接入新运行；未核验输出在界面与报告中状态明确。
- 改变变量处理或样本后，旧结果被标为过期；结果后改变方案保留理由和原结果；新会话能够读取文件接续。

最终验收包括真实宿主中的自然语言任务。单元测试、生成了代码或程序成功退出均不能替代上述使用验收。
